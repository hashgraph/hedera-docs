<Warning>
**This server's signing model has changed.** Transactions are now approved and signed **in your
own wallet** — the server no longer returns transaction bytes for you to sign yourself. The
`x-hedera-account-id` header is no longer used and is ignored; your account now comes from a
wallet sign-in instead. The endpoint URL is unchanged, but existing connections must sign in
again with a wallet before any tool will work.
</Warning>

<Note>
**Network:** The hosted server is connected to **Hedera Testnet only**. For Mainnet integrations, run the [self-hosted MCP server](https://github.com/hashgraph/hedera-agent-kit-js/tree/main/examples/modelcontextprotocol).
</Note>

## Overview

The **Hedera Network Hosted MCP Server** provides a managed, remote instance of the Hedera Agent Kit exposing its tools via the [Model Context Protocol (MCP)](https://modelcontextprotocol.io/). Any MCP-compatible client that supports OAuth 2.1 — such as Claude, Cursor, Codex CLI, ChatGPT Desktop, or a custom AI application — can integrate Hedera network capabilities without deploying or maintaining local agent infrastructure.

<Note>
**Non-custodial by design.** The server holds no Hedera keys of any kind, never submits a transaction, and never sees your signature. It builds and freezes transactions, then delivers them to your wallet — your wallet signs *and* broadcasts. Your wallet approval is the only authorization boundary: nothing moves without you approving what your wallet displays.
</Note>

## Before you start

- A [Hedera Testnet account](https://portal.hedera.com/dashboard).
- A [HIP-820](https://hips.hedera.com/hip/hip-820)-compatible wallet — a mobile wallet (like HashPack or Kabila Wallet) for WalletConnect QR pairing, or a browser extension wallet.

## Connect your client

Register the hosted server the same way you'd add any remote MCP server. No account ID or other header goes in the config — the server no longer accepts one, since your account is proven by your wallet during sign-in.

## Sign in with your wallet

The server is an OAuth 2.1 authorization server whose "login form" is a wallet. The first tool call your client makes is rejected with `401`, which triggers this flow automatically:

1. Your client opens a browser to the server's sign-in page.
2. You may see an interstitial asking you to confirm you started this connection from your MCP client — this is expected, not a phishing attempt. Continue.
3. Pair your wallet — scan the WalletConnect QR code with a mobile wallet, or use the browser-extension button if you have one installed.
4. Your wallet prompts you to approve a **sign-in message**. This is a single-use, domain-bound nonce — **approving it moves no funds**. It only proves you control the account.
5. The server verifies the signature against your account's key on the mirror node and issues an access token. Your client returns to normal use, now scoped to your account.

## Example prompts

Try these once you're connected — one that triggers your wallet, one that doesn't.

This writes to the network, so it triggers your wallet to approve and sign the transaction:

```text
Create a topic with memo "test"
```

This only queries network state, so your wallet is **not** triggered — read-only queries never need a signature:

```text
What's my HBAR balance?
```

## How transactions work

Every transaction tool (transferring HBAR, creating a topic, minting a token, and so on) builds the transaction, freezes it, and **delivers it to your wallet for approval in one call**, returning a `requestId` instead of blocking. Your agent then checks on it:

```
transfer_hbar_tool({ to, amount })   ->  { requestId, summary, walletVerifiable, ... }
check_signing_status({ requestId })  ->  awaiting_approval | confirming | executed | ...
```

| Status | Meaning |
| :--- | :--- |
| `awaiting_approval` | Delivered to your wallet; waiting on your approval |
| `confirming` | Your wallet broadcast it; the server is checking the mirror node |
| `executed` | Confirmed on the mirror node |
| `rejected` | You declined it in your wallet |
| `failed` | Reached the network but failed on-chain |
| `expired` | The ~180 second validity window lapsed — ask your agent to try again |
| `needs_reauth` | Your wallet session ended — reconnect (see [Troubleshooting](#troubleshooting)) |

<Note>
`executed` means the mirror node confirmed it, not just that your wallet said it broadcast it — so a stale approval that never lands is reported honestly rather than as a false success. The ~180 second window matches Hedera's transaction validity window, so approve promptly.
</Note>

### Wallet tools

| Tool | Purpose |
| :--- | :--- |
| `wallet_status` | Returns your connected `accountId`, `network`, and wallet session expiry |
| `check_signing_status` | Checks (and waits on) the outcome of a `requestId` from a write tool |
| `sign_with_wallet` | Raw-bytes escape hatch — normally unnecessary, since write tools deliver to your wallet automatically |

<Info>
**Not every transaction type is fully decodable in a wallet.** Contract calls and file operations come back with `walletVerifiable: false` — for these, your wallet's display isn't an independent check of what the transaction actually does. Review what your agent tells you it's building before approving.
</Info>

## Available tools

The Hedera network server comes pre-configured with all core Hedera plugins. Exposed tool categories include:

- **Accounts:** create accounts, update keys, transfer HBAR, manage allowances, query balances.
- **Tokens (HTS):** create, mint, transfer, associate, and query fungible and non-fungible tokens.
- **Smart Contracts (EVM):** deploy, call, and query ERC-20 and ERC-721 contracts.
- **Consensus (HCS):** create topics, submit messages, and query topic info.
- **Transactions & Misc:** query transaction records, exchange rates, and node fees.

See the [Plugins](/solutions/ai/agent-kit/plugins) page for the complete list of tools and their parameters.

## Troubleshooting

**"The connector's server isn't responding" / "Couldn't connect to the server"?**
- This almost always means your **wallet session has ended**, not that the server is down — for example, because you removed the dApp session from your wallet, or the session simply expired.
- The client does not currently prompt you to reconnect on its own, and restarting it won't clear the stale session.
- Fix: open **Settings → Connectors**, find the Hedera entry, click it, choose **Disconnect**, then **Connect** again and complete the wallet sign-in.

**Removed the wallet's dApp session and now nothing works?**
- Disconnecting the session in your wallet (for example, removing the dApp from HashPack) ends the server-side session too. Reconnect the MCP server as above to sign in again.

**Reconnected but never asked to sign in again?**
- Re-adding or reconnecting the server doesn't always force a new wallet login — if a valid wallet session still exists, it's reused automatically. This is expected.

**A signing request came back `expired`?**
- You have about 180 seconds to approve a transaction in your wallet. If it lapses, ask your agent to re-run the action.

**Tools not appearing after connecting?**
- Restart your client after adding or reconnecting the server.

## Limitations

- **Testnet only.** The hosted instance does not connect to Mainnet. Run the self-hosted server for Mainnet usage.
- **Single-key accounts only.** Threshold and key-list accounts aren't supported for wallet sign-in.
- **No spend policies.** There are no per-transaction or per-day caps or recipient allowlists — your wallet approval prompt is the spending control, so review each request.
