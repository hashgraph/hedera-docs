Settle a trade between a seller and a buyer where the security leg and the payment leg move in **one** Hedera transaction. If either leg fails a check (missing KYC, frozen account, insufficient balance), nothing moves. No escrow contract, no settlement agent, and settlement is final in seconds.

## Overview

{/* Cover:
    - What DvP is, in two sentences: delivery of the security against payment of cash, guaranteed together.
    - The problem it removes: principal / settlement risk when one leg goes first; today solved by CSDs and clearing houses with T+1/T+2.
    - Why it is better on Hedera: a native TransferTransaction carries both legs atomically; KYC/freeze keys apply to both legs; scheduled transactions collect the counterparty signature asynchronously.
    - Contrast in one line with EVM-style DvP (escrow contract, approvals, two steps). */}

The workflow has three actors:

* **Issuer**: creates the security token (with KYC and freeze keys) and the payment token, and grants KYC to investors
* **Seller**: holds the security, proposes the trade, and signs first
* **Buyer**: holds the payment token, reviews the proposed trade, and signs second

The trade lifecycle:

1. The Issuer creates the security token and the payment token
2. The Seller and Buyer associate both tokens; the Issuer grants them KYC on the security
3. The Seller proposes the trade as a scheduled transfer containing both legs and signs it
4. The Buyer reviews the scheduled transfer on-chain and signs it
5. The network executes both legs in one transaction, or rejects both

```text
Issuer                       Seller                     Hedera network                  Buyer
  |                            |                              |                           |
  |-- create SEC + tUSD ------------------------------------->|                           |
  |-- grant KYC (SEC) --------------------------------------->|                           |
  |                            |-- ScheduleCreate(           |                           |
  |                            |     SEC  Seller -> Buyer    |                           |
  |                            |     tUSD Buyer  -> Seller)  |                           |
  |                            |   + Seller signature ------>|  scheduleId (pending)     |
  |                            |                              |<--- ScheduleSign ---------|
  |                            |                              |  both legs execute,       |
  |                            |                              |  or neither               |
```

| Web UI | Next.js with Issuer, Seller and Buyer views (scaffold-hbar) |
