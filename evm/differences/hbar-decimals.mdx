## **Overview**

Managing token decimals is critical when working with HBAR, HTS tokens, and ERC tokens on Hedera, as each system has distinct precision standards. These differences impact how token balances are calculated, displayed, and transferred across various tools and environments.

***

## Token Decimal Comparison and API Context

HBAR has two scales on Hedera. Inside the network, including inside the EVM, HBAR is counted in **tinybars** (8 decimals, 1 ℏ = 10⁸ tinybars). The JSON-RPC relay presents HBAR to Ethereum tooling in **weibars** (18 decimals, 1 tinybar = 10¹⁰ weibars) so that wallets and libraries such as ethers and viem work unchanged. When an Ethereum transaction executes, the network divides its `value` by 10¹⁰ to get tinybars before the EVM runs; the relay multiplies tinybar amounts by 10¹⁰ when it returns balances and gas prices.

| Where the value appears | Decimals | Notes |
|---|---|---|
| Hedera API (HAPI) and SDKs | 8 (tinybars) | Native representation of HBAR. |
| Inside Solidity: `msg.value`, `address.balance`, `call{value: ...}` | 8 (tinybars) | The network converts the transaction `value` from weibars to tinybars before the EVM runs. Ethereum literals such as `1 ether` are 10¹⁸ tinybars here, which is 10¹⁰ HBAR. |
| JSON-RPC wire: transaction `value`, `eth_getBalance`, `eth_gasPrice` | 18 (weibars) | What wallets, ethers, and viem send and receive. In ethers, `parseEther("1")` is 1 HBAR. |
| Function arguments that carry HBAR amounts | Whatever the contract expects | Raw ABI values; nothing converts them. A contract that compares an argument with `msg.value` should take tinybars. |
| HTS tokens | Set by the token creator | Chosen at token creation; not limited to 8. |
| ERC tokens | 18 by default | Standard ERC-20 default unless the contract overrides `decimals()`. |

**Key impacts**:

* Inside a contract, never scale `msg.value` by `10**10`. Compare it with tinybar amounts directly, such as the result of the [Exchange Rate system contract](/evm/hedera-services/system-contracts/exchange-rate).
* Multiply by `10**10` only when you hand a tinybar amount to JSON-RPC tooling as a transaction `value`.
* The relay rejects a nonzero `value` smaller than one tinybar (10¹⁰ weibars) with `VALUE_TOO_LOW`. Any precision finer than a tinybar is dropped when the network converts the value.
* HBAR fees are always calculated in tinybars, regardless of the API or service used.

***

## Conversion Helpers

Use these helpers when you move an HBAR amount between the two scales, for example when a contract receives a weibar amount as a function argument from a front end. Don't apply them to `msg.value` or `address.balance` inside a contract: those are already in tinybars.

**Code Example: Decimal Conversion Helpers**

```solidity wrap
// Convert from 18 decimals (weibar/wei) to 8 decimals (tinybar)
function convertToTinybar(uint256 weiAmount) public pure returns (uint256) {
    // 1 tinybar = 10^10 weibar
    return weiAmount / (10 ** 10);
}

// Convert from 8 decimals (tinybar) to 18 decimals (weibar/wei)
function convertToWei(uint256 tinybarAmount) public pure returns (uint256) {
    return tinybarAmount * (10 ** 10);
}
```
